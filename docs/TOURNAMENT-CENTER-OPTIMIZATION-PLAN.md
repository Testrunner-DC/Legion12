# 赛事中心完整优化方案

## 1. 目标与边界

赛事中心应覆盖玩家从发现赛事、报名、赛前签到、参赛、申诉到查看历史的完整路径，也应覆盖主办者从创建草稿、发布、控场、裁决到归档的完整路径。

本轮不定义新的全局视觉风格。页面沿用现有颜色、间距、字体和控件变量，只确定信息层级、状态反馈、操作优先级和响应式要求，等待全站视觉统一时再集中调整。

核心产品原则：

1. 报名只确认参赛意愿，不要求提交牌库。
2. 玩家在赛前签到时选择牌库；签到成功后服务端锁定牌库快照。
3. 主办者在赛前和赛中都可移出玩家，并可选择禁止该玩家再次报名本场赛事。
4. 主办身份通过“发起交接—接任者确认”完成，交接历史可审计。
5. 赛事对局使用与排位相同的五项计时参数和权威计时逻辑，不再使用简单的每轮总时间。
6. 列表只返回摘要，详情按稳定赛事代码访问，避免赛事规模增大后列表负载随全量参赛者和赛程膨胀。

## 2. 信息架构与页面

### 2.1 赛事中心 `/battle/tournaments`

一级入口分为：

- **发现**：公开且尚未结束的赛事，支持名称、代码、主办者、赛制和时间范围筛选。
- **我的赛事**：本人作为参赛者、主办者或裁判参与的赛事，并优先显示需要本人处理的项目。
- **历史**：已完成或已取消的公开赛事归档。
- **主办管理**：本人主办的赛事，集中显示待签到、待处理案件和待确认赛果。
- **创建赛事**：五步创建流程，支持本地草稿、常用赛制模板、预览和不落库校验。

列表卡片只包含赛事名称、代码、状态、赛制、计划时间、主办者、正式席位人数、候补人数、本人角色和待办标记。分页上限由服务端控制，列表不携带参赛者、轮次、牌库、裁判记录等详情集合。

### 2.2 赛事详情 `/battle/tournaments/:code`

详情使用稳定赛事代码，可直接分享。旧地址 `/battle/tournaments?code=...` 自动跳转到新详情地址。

详情页分为：

- **概览**：状态、阶段、主办者、人数、时间、延期记录及“你的下一步”。
- **赛程**：轮次、桌次、签到、进入对局、普通观战、暂停状态。
- **排名**：当前轮排名、最终排名和淘汰树结果。
- **参赛者**：正式席位、候补顺位、签到锁牌、移出和禁报名状态。
- **规则**：规则快照、牌库公开规则、天灾范围、构筑限制和五项计时设置。
- **裁判台**：呼叫裁判、案件队列、分派、裁决、申诉和利益冲突回避。
- **主办管理**：生命周期、开赛检查、延期、取消、主办交接和结赛归档。

赛事结束或取消后，公开赛事继续提供赛程、排名与可公开牌库；内部处置理由、裁判备注和交接历史仍按权限隐藏。

## 3. 创建流程

创建采用五步流程：

1. **基础信息**：名称、公开方式、计划时间、简介。
2. **赛制与名额**：单败、瑞士轮、瑞士轮加 Cut、人数上限、轮数和 Cut 人数。
3. **规则与牌组**：规则版本、牌库公开策略、天灾范围、签到窗口。页面明确提示“报名不提交牌库，赛前签到时锁定”。
4. **工作人员与计时**：选择裁判，并配置与排位一致的五项计时参数。
5. **预览与创建**：先调用不落库校验，通过后执行正式创建。

未完成内容保存为本地草稿。预设模板只写入赛制相关默认值，用户仍可逐项修改。草稿不是服务端已发布赛事，不占赛事代码和平台版本。

## 4. 生命周期

权威生命周期为：

| 阶段 | 允许操作 | 退出条件 |
| --- | --- | --- |
| 草稿 | 编辑创建表单、套用模板、预览 | 正式创建 |
| 报名开放 | 报名、退出、进入候补、延期 | 主办关闭报名或进入赛前签到 |
| 报名关闭 | 维护名单、移出、禁报名、重新开放 | 进入赛前签到或重新开放 |
| 赛前签到 | 玩家选择并锁定牌库、主办检查名单 | 开赛或退回报名阶段 |
| 进行中 | 轮次签到、进入桌次、观战、暂停、裁判、移出 | 全部轮次完成后进入成绩确认 |
| 成绩确认 | 复核排名和赛果、处理未结案件 | 确认归档或退回进行中 |
| 已完成 | 公开归档、履历、导出 | 终态 |
| 已取消 | 记录理由、终止活动桌次、归档 | 终态 |

只允许表中相邻或明确的回退转换。服务端校验版本号，避免多个工作人员同时操作时用旧页面覆盖新状态。为兼容既有赛事，旧的直接开赛和直接完成接口仍可执行；新界面始终引导经过赛前签到和成绩确认。

## 5. 报名、签到和候补

### 5.1 报名

- 报名请求不携带牌库，正式席位未满时直接进入名单。
- 正式席位已满时自动进入候补，并记录稳定顺位。
- 报名关闭、赛事开始、赛事完成或取消后拒绝新报名。
- 被禁止再次报名的玩家即使持有分享代码也不能报名。

### 5.2 候补

- 正式玩家赛前退出或被移出时，按候补顺位自动递补一人。
- 候补玩家不能赛前签到，也不会进入首轮配对。
- 递补后记录时间，玩家在“我的赛事”看到需要完成签到锁牌的待办。

### 5.3 赛前签到与锁牌

- 只有正式席位玩家可以签到。
- 签到时提交牌库名称或代码，服务端解析并校验构筑规则，保存不可变牌库快照和锁定时间。
- 重复提交相同牌库视为幂等成功；尝试更换已锁定牌库会被拒绝。
- 开赛检查至少要求两名正式玩家完成签到并具有有效锁牌快照。

## 6. 主办者与工作人员治理

### 6.1 移出与禁报名

主办者或拥有全局赛事管理权限的人员可在赛前和赛中移出玩家。操作必须填写理由，并可选择：

- 仅移出：玩家离开本场赛事，但在报名阶段可再次报名。
- 移出并禁报名：同时写入本场赛事禁报名记录，玩家不能再次加入。
- 解除禁报名：必须填写理由并写入审计记录。

赛中移出后，该玩家失去进入赛事房间的资格；下一轮生成时不再进入配对。已发生的赛果和审计事件保留。

### 6.2 主办身份交接

- 当前主办者从可用账号中选择接任者并填写原因。
- 系统生成有期限的待确认请求；接任者接受后才转移主办身份。
- 接任者可拒绝；新的交接请求使旧请求失效。
- 交接不会重置赛事版本、规则快照、名单、赛程、案件或历史记录。
- 交接完成后，原主办者立即失去本场主办权限，除非仍是裁判或拥有全局权限。

## 7. 计时规范

赛事对局复用排位的权威计时模型和持久化恢复能力，配置项为：

1. 每名玩家总可用时间。
2. 单次操作时间。
3. 断线重连宽限。
4. 天灾决定时间。
5. 调度决定时间。

服务端根据当前行动者结算计时，客户端只展示权威投影。单桌暂停时冻结总时间、操作时间和断线宽限；暂停状态、原因和时间点写入既有对局运行快照，服务重启后继续保持暂停。恢复时不计入暂停期间经过的时间。

裁判仍可执行有限补时，补时写入赛事桌次裁决记录，并同步到对局计时。旧字段“轮次总分钟”仅用于历史数据展示和兼容，不参与新赛事对局倒计时。

## 8. 裁判工作流

- 桌内玩家可以按规则、技术问题、迟到或赛果类别呼叫裁判，并标记普通或紧急。
- 裁判台展示案件队列、桌号、提交者、紧急度、状态和受理人。
- 主办者或裁判可分派案件；正在参加该桌的工作人员不能受理或裁决自己的桌次。
- 裁定包含对玩家可见的结论和仅工作人员可见的内部备注。
- 桌内玩家可对已裁定案件申诉一次；申诉后案件重新进入待处理状态并清空原受理人。
- 单桌暂停独立于整轮暂停，用于规则核查，不影响其他桌次。

## 9. 观战、历史与导出

- 公开赛事的进行中桌次允许普通账号观战，仍遵循对局既有隐藏信息投影。
- 凭代码赛事只有工作人员和参赛者可读取详情或观战。
- 已完成和已取消赛事进入历史归档。
- 个人履历统计参赛、主办、执裁次数及胜负平，并列出历史赛事和最终名次。
- CSV 导出按轮次和桌次输出双方、赛果、状态及关联录像 ID，便于线下存档与复核。

## 10. 数据、性能与可靠性

- 所有写操作沿用赛事版本前置条件、幂等键和审计上下文。
- 对局赛果沿用现有 Journal、outbox 和检查点，不建立第二套回写链路。
- 赛事列表和个人履历都使用服务端分页，页大小限制为 1–100；列表只返回摘要，详情按赛事代码单独读取。
- WebSocket 资源变更通知触发刷新；页面重新可见时补一次刷新，不增加高频轮询。
- 256 人赛事的列表响应仍只包含一个摘要对象；参赛者和赛程仅在详情中返回。
- 取消赛事时，活动房间由服务器作权威无胜者结束并保存录像，不生成虚假赛果。

## 12. 发布前检查

1. 后端赛事全流程测试全部通过，包括候补、生命周期、取消、裁判回避、申诉、单桌暂停、普通观战、摘要分页、256 人规模及副作用失败/重启恢复。
2. 平台完整测试通过，确认既有牌库锁定、主办交接、赛果 outbox 与恢复逻辑无回归。
3. 前端类型检查、生产构建、性能架构锁和 UI 契约检查通过。
4. 检查变更中没有删除既有赛事结果持久化文件或绕开资源通知机制。
5. 前端赛事静态契约确认主办/裁判权限拆分、后台工作台命名、本人桌次呼叫与申诉、中文映射和参数范围；再人工走查桌面和窄屏下的报名、签到、候补提示、主办交接、裁判案件和导出入口。
