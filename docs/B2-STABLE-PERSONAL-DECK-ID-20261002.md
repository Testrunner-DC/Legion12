# B2｜个人牌库稳定 ID（2026-10-02）

## 边界与身份

- 个人牌库的身份是服务端生成的账号内 `id`，名称仅是可修改的显示字段；`revision` 是每次更新和删除的并发前置条件。账号内规范化名称仍唯一。
- 新客户端用 `POST /api/decks` 新建，用 `PUT /api/decks/by-id/{id}` 携带 `expectedRevision` 原子更新（含改名），用 `DELETE /api/decks/by-id/{id}?expectedRevision=…` 删除。失配返回冲突，不用“另建新名再删旧名”模拟改名。
- 登录同步以服务端列表为权威。本地各对战模式的已选对象保存 ID；只有旧名称缓存与服务端构筑正文完全一致，或旧缓存已带有相同 ID，才自动迁移选择。无法确认的旧选择不按同名猜测，需玩家重选。新建、复制、导入或保存不暗改各模式选择。
- 编辑器入口同时保留可读名称和个人 ID，刷新与改名优先按 ID 回到同一对象。本机草稿记录基底 ID/revision；旧版无 ID 草稿仍可读取，但作为独立草稿恢复，不凭名称误绑新的服务器对象。
- 公开牌库 `publicationId` 与私人 `id` 分域。复制获得新私人 ID；作者更新自己的公开来源时复用其现有私人 ID。房间与匹配队列已保存提交时的完整构筑快照，不再按当前名称重新查找。
- 赛事赛前签到的新客户端提交个人 `deckId`。服务端按当前账号加 ID 严格解析；ID 已删除、跨账号或失效时拒绝，不回退到同名或牌库码。签到成功后只使用独立锁牌快照；内部保存来源 ID 供幂等和审计，不向其他玩家的赛事视图外显。

## 迁移、兼容和恢复

- 现有 `account_decks` 增加 `deck_id/revision`，在 SQLite 事务内为活跃旧行补齐，校验 ID、名称和正文哈希，再提交存储状态。迁移前在相同制品盘原子写入完整压缩 JSON 备份及 ID 映射；备份可实际解压、用旧 JSON 导入入口恢复。
- 已迁移后若临时回滚旧二进制，旧程序仍可插入没有 ID 的行。再次启动新版会扫描并补齐这些行，在补迁移前刷新完整备份；不得仅凭“迁移状态已完成”跳过检查。
- 旧按名称 PUT/DELETE 路由暂留兼容，但没有 `revision` 防护。所有新流程只使用 ID 路由；旧客户端若以“新名 PUT＋旧名 DELETE”操作，稳定身份不能得到保证，因此退场窗口应在客户端版本覆盖后另行裁定。
- 失败时事务回滚并从最后已提交快照恢复内存；保留数据库、镜像、迁移备份和审计，不以旧备份覆盖新的已提交事实。生产部署前需对实际数据副本完成迁移预演与恢复读回；本批开发不触碰线上数据。

## 验收范围

- 服务端：改名保持 ID、版本递增、重名/旧版本/跨账号失败；旧 SQLite 行补 ID、旧二进制写入后再升级、完整备份实际恢复；提交前故障不留下半改名或丢牌。
- 赛事：旧名被复用后签到仍锁原 ID；删除原 ID 不回退；跨账号 ID 被拒；锁牌后私人牌库改名或删除不改变赛事快照、重启与重试结果。
- 前端：多模式选择与改名连续性、公开复制新身份、旧草稿可读、账号隔离、异步同步不覆写新状态；旧标签页删除按所选 ID/revision，旧名复用不误删另一副。
