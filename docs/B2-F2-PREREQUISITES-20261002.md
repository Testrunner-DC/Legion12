# B2 / F2 前置盘点（2026-10-02）

本文件是设计与证据准备，**不是 B2 稳定 ID 迁移或 F2 按对象持久化的实施授权**。本次未读取线上玩家数据、未改变数据库结构、未部署。

## B2：个人牌库稳定 ID

### 已核对的现状

| 边界 | 当前身份与行为 | 迁移时必须保护的事实 |
| --- | --- | --- |
| 账号 API | `GET/PUT /api/decks` 返回/写入按 `name` 识别的牌库；`DELETE /api/decks/{name}` 按名称删除。服务端 `UpsertDeck` 对同账号同名（忽略大小写）覆盖，否则新增。 | 改名须是**同一对象的一次原子更新**；同账号名称冲突不得误覆盖另一副牌库。 |
| SQLite / 镜像 | `account_decks` 以 `(account_id,name_key)` 为主键；`DeckRow` 和 `L12AccountDeckView` 都没有个人牌库 ID。`Save()` 在同一事务中同步牌库域、平台快照与审计，之后写 JSON 兼容镜像。 | 新 ID 需要贯穿行、平台快照/镜像与恢复；迁移失败不能留下半写数据，也不能削弱只读回退。 |
| 编辑器 | `activeDeckName` 是当前对象身份；改名先保存新名称再删旧名称，删旧失败时保留两副。草稿 `baseDeckName` 用于恢复与冲突提示。 | 保存失败、断网、刷新、账号切换和草稿恢复都不能丢构筑；“另存为”必须创建新 ID，而非原对象改名。 |
| 本地缓存和出战选择 | `loadSavedDecks` 返回以名称为键的对象；休闲、排位、好友房、沙盒等作用域选择值保存在账号隔离的 localStorage 名称键中。 | 改名后每个作用域仍选择原对象；不得悄悄改动别的模式选择，游客和旧缓存有明确迁移/失效策略。 |
| 赛事和公开牌库 | 赛前签到以名称选账号牌库，但锁定后保存牌库快照；公开牌库已有独立 `publication_id`/短码，复制会生成个人副本。 | 不能把公开版 ID 误用作个人牌库 ID；既有赛事锁牌快照和历史版本不应随个人改名重写。 |
| 对战房间 | 房间选择时提交构筑快照，已开局的记录保留牌库名/卡组事实。 | 个人改名不能追溯改变已开始或已记录的对局。 |

### 独立实施前的退出条件

1. 在合成副本上盘点同账号大小写/空白归一化名称冲突、缺失字段及旧镜像恢复；给每个既有个人牌库分配一次稳定 ID，建立 `(account_id,deck_id)` 主键及账号内名称唯一约束，提供可逆映射和迁移前备份。ID 不从名称或牌表哈希推导。
2. 先定义并冻结 API：更新须带 `deck_id` 与版本/预期值；新建由服务端分配 ID；改名冲突有确定错误；删除必须按 ID 且复验归属。旧 API 的读取/退场期和回滚条件单独列明，不能在客户端先行更换身份键。
3. 逐项迁移编辑器、账号缓存、各模式出战选择、草稿基底、公开来源、复制和赛事签到引用。客户端迁移只在服务器权威列表读回并确认 ID 后提交；损坏或歧义的旧名称引用显式提示，绝不猜测对应对象。
4. 故障注入：数据库事务提交前/后、镜像写失败、网络响应丢失、并发改名、重名、旧标签页写入、跨账号切换。验收“只一副、原选择不变、旧数据可读、失败无丢失”，并以新旧版本恢复演练证明回滚。

**当前裁定：**完成依赖盘点；未运行数据迁移，也未将 B2 列入自动实施队列。下一步需要针对上述 API/回滚合同批准独立高风险批次。

## F2：按对象持久化的取证门槛

F1 的合成基准见 [平台存储增长基线](PLATFORM-STORAGE-GROWTH-BASELINE-20261002.md)：账号/个人牌库/公开版/赛事同时增长到 `150/1200/60/30` 时，牌库保存 P95 为 34.60 ms、后台写入 P95 为 39.59 ms，点赞仍约 4–5 ms。`PersistTransactionalData` 每次一般写入均调用 `PersistDeckDomainSnapshot`，它遍历所有个人及公开牌库；但 F1 只给出 SQL 次数**下界**，并未测得精确次数或累计写入字节。四个规模维度同步变化，也不能据此将耗时单独归因于牌库域。

### 可执行的下一轮测量（仍不实施 F2）

1. 只在 D 盘合成库加入测量器，分别保持其余维度不变，仅放大账号、个人牌库、公开版、赛事之一；保留 F1 的登录、保存、点赞、后台写入、锁等待与恢复口径，并增加并发写读矩阵。
2. 在存储命令边界记录每次操作的 `SELECT/INSERT/UPDATE/DELETE` 次数、受影响行数、事务持续时间与提交前后 SQLite/WAL/镜像累计写入字节；测量器不得把逐条 SQL 或完整牌库内容写进报告。文件最终大小与累计写入量分开报告。
3. 对比同一操作的预热、P50/P95/P99、锁等待、分配量、错误率及恢复时间；至少重复独立运行并记录机器、提交 SHA、数据生成参数。将具体瓶颈归到域和代码路径，列出可接受预算，避免以小样本 P99 冒充线上 SLA。
4. 在故障注入下核对事务、版本/赛季结算栅栏、镜像恢复、快照校验、审计及跨域引用。只有测量证明某个高频域的全量写入造成不可接受成本，才提出该域单独迁移方案、双读校验和回滚演练。

**当前裁定：**F2 的目标域和架构变更尚未获证据支持；不改变 `Save()`、镜像、事务、SQLite 结构或恢复流程。后续是否实施 F2，待补测报告与独立批准。
