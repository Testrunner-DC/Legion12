# L12 后台控制底座设计

> 本文是目标设计，不声明尚未落地的能力已经实现。实施不得改变卡效语义、对局状态机或正式房间权限；GM 仍限单人测试沙盒。现状与证据见 [ADMIN-GAP-MATRIX.md](ADMIN-GAP-MATRIX.md)。

## 1. 边界与原则

控制面管理账号、内容、Bug、赛事、发布和受控诊断；数据面负责正式对局、规则结算与玩家可见状态。控制面不得直接写入进行中正式对局状态、玩家隐藏信息或规则内核。所有有副作用的动作必须经过服务端命令入口，先授权、再校验、后执行并记录结果；浏览器显示/隐藏不能构成权限。

GM 是诊断例外而不是生产管理员工具：仅沙盒创建者会话可调用，命令继续进入既有权威规则/记录链；禁止新增“管理员接管正式房间”“修改正式手牌/生命/卡效”的能力。

## 2. 认证与 RBAC

保留现有 bearer 会话作为过渡，迁移到可撤销、带 `sessionId`、过期时间、认证强度和权限版本的会话。密码、MFA、账户禁用、会话撤销、速率限制和登录/拒绝事件必须由服务端实施。

平台长期身份固定为 `player` 与 `admin`，不能由前端昵称或 localStorage 推导。玩家创建赛事后在该赛事内临时成为主办者；裁判由主办者从已接受好友中指定，也只在该赛事内生效。账号身份/状态和赛事操作不要求另一人审批，但必须经过服务端权限/作用域校验、版本前置、幂等和审计。内容正式发布、生产发布、审计归档等可影响全站或外部系统的高风险动作继续保留复核。`admin` 不是绕过正式对局规则的权限。

| 能力 | 最低权限 | 额外约束 |
| --- | --- | --- |
| 查/分派 Bug | admin | 对局附件按最小披露裁剪 |
| 内容草稿 | admin | key 白名单、预览环境 |
| 内容发布 | admin + 另一名 admin | 双人复核、批次与回滚点 |
| 赛事裁决 | 本场 organizer/referee | 赛事作用域、理由与不可变审计；无需另一人审批 |
| 账号身份/状态 | admin | 不能移除最后一名 admin；直接执行并审计 |
| 发布/回滚 | admin + 另一名 admin | 仅已验证工件、变更单、干运行 |
| 沙盒 GM | sandbox controller | 保持现有单房间/单会话服务端校验 |

## 3. AdminCommandBus

新增内部服务层 `AdminCommandBus`；HTTP/后台 UI 仅负责把请求转为已验证命令。命令信封应至少包含：`commandId`、`idempotencyKey`、`type`、`actor`、`requestedAt`、`scope`、`reason`、`dryRun`、`expectedVersion` 与 typed payload。处理顺序：认证 → 权限/作用域 → 参数与状态前置条件 → 幂等去重 → 策略/审批 → 事务执行 → 领域事件与审计 outbox → 响应。

命令需声明风险等级和执行策略。低风险（保存草稿、Bug 评论）直接执行；账号身份/状态与赛事动作按产品裁定也直接执行，但仍需幂等、版本前置、保护条件和审计。内容正式发布、生产发布、审计归档等跨全站或外部系统的高风险动作使用 `requested → approved/rejected → executed/failed/cancelled`。命令失败也写审计，dry-run 永不修改数据。

## 4. 审计与可观测性

审计账本与业务表分离，追加写入，包含 commandId、关联/因果 ID、actor、权限快照、目标、前后摘要（敏感字段脱敏）、结果、拒绝原因、客户端/服务版本和时间。保留策略、归档与只读访问权限明确化；不能继续依赖可随业务 JSON 一同截断的内嵌列表作为唯一审计证据。

为命令、发布、赛事裁决与 GM 建立指标和告警：失败率、拒绝率、审批积压、发布验证失败、审计写入失败。审计不可用时，高风险命令应失败关闭。

## 5. 领域工作流

### Bug

状态机：`new → triaged → confirmed → in-progress → resolved → verified → closed`，允许带理由的 reopen。每次转换强制记录负责人、严重度、复现材料、关联对局（按权限裁剪）、修复变更/回归证据与验证人。去重、SLA、敏感信息标记和导出权限由服务端执行；遗留文件反馈需导入或显式关联，避免双轨丢单。

### 内容

内容实体使用受控 key、版本、草稿、预览、审批、已发布版本和回滚指针。一次发布作为单批次，不能由前端循环多个单键请求代替原子批次。媒体、FAQ/规则版本和定时发布在审计与回滚机制完成后再接入。

### 赛事

将浏览器 localStorage 原型迁移为服务端赛事聚合：赛事、规则快照、报名、资格、配对、轮次、对局关联、裁决和赛果。所有变更使用账户 ID，不使用昵称；裁判仅能处理被授予的赛事。配对/结果采用乐观版本或串行事务，裁决保留理由与审计。上线前必须明确牌表可见性、弃赛、重赛、争议与榜单结算规则。

### 发布与运维

控制面只编排已存在的受控发布工件，不在网页中执行任意 shell。发布记录工件提交、哈希、环境、审批、干运行、健康检查、WebSocket 冒烟、结果和回滚目标。运行态只读视图来自受认证的健康/指标适配器；密钥、服务器路径和部署凭据绝不进入前端或审计明文。

## 6. 数据模型与协议

建议持久化迁移至支持事务/迁移的存储，并保留导入 `platform.json` 的一次性工具与校验。核心表：`accounts`、`sessions`、`roles`、`permissions`、`role_bindings`、`admin_commands`、`command_approvals`、`audit_events`、`bug_reports`、`bug_events`、`content_entries`、`content_versions`、`tournaments`、`tournament_rounds`、`tournament_matches`、`rulings`、`release_runs`。对局记录仍由既有 recorder 管理，控制面只保存引用和授权元数据。

版本化 API 使用 `/api/admin/v1`。所有变更请求要求 `Idempotency-Key` 和 `If-Match`/版本；成功返回命令与资源版本，异步动作返回 `202 + commandId`。读取 API 分页、筛选和作用域裁剪；错误使用稳定 code、可显示 message、correlationId。禁止通过通用任意 key/value 或前端角色字段改变生产资源。

## 7. 迁移阶段

1. **基础与观察**：为现有 admin API 建立权限矩阵、命令审计 outbox、关联 ID、会话撤销和回归测试；不改变卡效/对局路径。
2. **命令化现有能力**：将账号、Bug、内容、卡效审查迁入 `AdminCommandBus`，实现幂等、版本冲突、审批与批次内容发布；双写/只读校验后切换。
3. **数据迁移**：从 `platform.json` 迁至事务存储，备份、校验、演练恢复、可回退读路径；审计独立保留。
4. **赛事服务化**：先只读导入 localStorage，再以账户 ID、赛事作用域、裁决审计和并发控制替代客户端写入；最后接对局/回放引用。
5. **发布编排与运行态**：接入已验证工件流程的只读状态、审批、干运行、发布和回滚记录；生产启用前完成故障演练。

每阶段必须保留前一阶段回滚方式，完成安全审查、迁移校验、权限负测、审计完整性验证和范围内的集成测试后才推进。

## 8. 验收标准

- 任一后台副作用都有服务端命令、幂等键、权限/作用域校验、结果和关联审计；拒绝与失败同样可追踪。
- UI 篡改角色、昵称、赛事数据或直接重放请求，不能越权、修改正式对局或泄露隐藏信息。
- 内容批次可以预览、审批、原子发布并回滚；部分发布不会留下未解释状态。
- Bug 能从提交到验证关闭关联复现材料与回归证据；遗留两条反馈通路有统一策略。
- 赛事在两并发管理操作下不产生重复配对或覆盖赛果，裁决可按赛事、操作者和理由追溯。
- 发布只能选择验证过的工件，干运行不改线上，失败健康检查可恢复到已知版本且记录完整。
- 沙盒 GM 仍被正式房间、观战者和非创建者拒绝；GM 记录与对局记录可关联且不授予生产修改能力。
