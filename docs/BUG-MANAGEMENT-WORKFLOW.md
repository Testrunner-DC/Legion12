# Bug 管理连接与确认流程

服务器 Bug 管理是玩家反馈、管理员审计和 Codex 修复工作的共同入口。它不授权自动修改代码或自动关闭反馈。

## 旧反馈以当前版本为准（用户2026-10-17更新，优先于下方历史取证流程）

- 用户明确：很多旧Bug已经随版本更新解决，不必逐条追究旧成因，当前版本正确即可收口。先复用现行正式提交、具名当前回归及已有用户裁定；同源有效证据可以同时覆盖多条旧反馈，不重跑完整套件，也不因有matchId就强制提取旧录像、私牌、旧检查点或补齐“报告版本→修复”的历史DAG。
- 已有对应修复、当前回归正确且修复包含在已核验正式版本中，按各报告独立`resolved/fixed_verified`；当前检查未复现、现行规则符合或信息不足以定义缺陷的，按既有用户授权`closed/rejected`并写清检查范围和原因。历史唯一成因不明不阻碍当前检查收口，但不得捏造原局重放、历史修复成因或原Bug从未存在，也不能仅凭同卡名设为duplicate。
- 只把当前仍可复现、当前验证不足、涉及未裁定规则／新增产品改动或真实数据安全风险的事项单独挂起。确有当前问题且原记录能回答未决问题时才进入后面的按需取证；旧记录过期或读取权限受限，不因此无限保留已有充分当前证据的旧反馈。
- 原文、15字段指纹、当前版本及具名证据仍保留；一批内统一准备、离线自检，再逐条一次preview/CAS/独立读回，单个post-CAS快照直接对账。不改原始历史、不把未部署本地修复当上线，不用规则回归冒称真实负载／真机验收通过。

## 固定流程

1. 只读拉取 `new`、`confirmed` 或指定条件的反馈，同时读取每条反馈的处理时间线。
2. 先检索 `docs/BUGFIX-REGISTRY.md`，再关联页面、房间、对局 JSON 和已有回归测试。
3. 向用户提交解决方案，列明根因假设、同类型扫描范围、拟修改公共层和防回滚测试。
4. 只有用户确认后才修改代码。
5. 验证通过后，在后台追加处理记录；状态变更、优先级、负责人和摘要均由服务器记录操作人、修改前后值和时间。
6. 按仓库约定同步 GitHub。部署仍须等待用户明确指令。

关单后的本地对账复用唯一 `work-items.json`、实际终态收据与一次新鲜队列快照；阶段计数以 `bugQueue.onlineClosedThisStage` 和当前阶段记录交叉核对，不从旧发布汇总命名空间取锚点。保留先前拒绝及原字节备份，不重交已成功关单；新增反馈单列，不能用待办净变化代替实际关闭数量。

同轮维护已有裁定与验收的本地进度：把实际用户决定写入对应 `humanDecision`，具名验收引用写入 `evidence`；已获批准的事项不再误留为等待用户，已本地通过但尚未上线的事项标记 `verify-live`。保留原始 `sourceStatus`、原文指纹及历史；本地进度变化不代替线上验收、不改变服务器状态，也不增加实际终态计数。复用已有证据，不为同步进度再次询问或重跑验收。

快照标签统一复用执行器实际的完整 `SnapshotTag`（例如 `phase-a355-...`），不手猜或复制一套收据文件名。已有对账标签与执行器不同的，摘要工具可传显式 `IntakeReceiptPath`，但路径和SHA必须精确匹配唯一工作清单中已经成功对账的 `latestIntake`；仅补摘要，不重新关单、登录拉取或重做已成功的工作清单对账。

内部状态别名的当前发布摘要须从同一组实际发布、独立核验及维护完成收据整体映射版本、PID、聊天能力与入口，不在新版本字段旁保留旧发布的PID或开关。历史原对象保存在已有字节备份，最新摘要明确区分线上版本、未部署的本地产品改动和本次仅对账动作；这只是一次本地状态校正，不重新部署、采样或增加发布门槛。

同一次关单对账也同步现存Bug摘要、旧续办计数和发布索引中的清单/关单引用；不在自由文本重复维护另一份当前数字，不改动已绑定的发布身份。摘要别名不存在时直接跳过，不因此新增状态文件或线上请求。

关单准备在原有一次离线自检内同时完成，不增加审批、扫描或第二条写路径：

- 明确输入是原始反馈数组还是唯一工作清单对象的 `items`；工作清单的原文哈希不能冒充API的15字段快照，后者仍绑定最新实际反馈。
- 固定执行器的SelfTest与Apply都显式传入同一已核验原始反馈数组`QueueSnapshotPath`及执行器精确`SnapshotTag`；不要把工作清单对象当数组，也不要在Apply漏传后重新拉取整队列。派生模板的“旧tag残留”校验不得误把合法新tag中的旧tag前缀判为残留；保留五组逐项发生变化和反向替换后整文件逐字相等、12函数原样及原合同，不能删完整性守卫。
- 统一schema2 proposal合同先验有界唯一ID、完整15字段/原文指纹、处置及说明；内存中新增的字典先按真实JSON输入归一化，避免把字典键误判为缺少对象属性。`fixed_verified`必须同时包含具名`regressionTest`、精确`fixCommit`及已独立核验的`deployedVersion`，不能等SelfTest赋值或网络阶段才发现缺字段；rejected与duplicate分别按其合同校验。
- duplicate还必须在认证前绑定执行器实际使用的`primary.id`与完整15字段期望指纹；主项已按规则/未复现rejected的，保持其真实处置，不伪装fixed。Main只在writer明确交回租约后读取最终不可变提案并核SHA，避免边写边执行；同一已写CAS的恢复仍只读，不因工具交付差异重复写。
- 复用现有关单执行根和`Test-ClosureProposalContract-v2.ps1`，其调用不可变的原15字段合同（3正/12负）并同轮预检服务字段归一化：fixCommit、regressionTest、deployedVersion、duplicateOf、closureDisposition均不超过500字符且无需trim；任一将被隐式截断/修剪就先离线拒绝（新增2正/10负），不等写后读回才发现差异。新输出根先解析祖先联接并核准物理D，C历史证据仅保留引用；本轮现有执行根为`D:/GPT/Legion12/artifacts/bug-closure-continuation-20261011/next-authority-batch-20261016/closeout`。实际写入仍是原preview→一次CAS→独立终态读回，单个post-CAS队列快照直接复用本地对账。若已写成功而读回工具失败，只读核对该原写，不重交CAS、不改写失败收据。脚本变更先解析AST、再离线自检；派生脚本须字面替换，不让生成语言的替换元字符改变PowerShell内容。
- 单反馈关单的并发版本必须绑定同一次权威读取的目标行，不能把预览正文与事务外返回的 ETag 当成原子快照。现有 `/api/admin/bugs/query` 在同一平台锁内返回 Items 与 PlatformVersion；预览后仅一次精确ID分页读取，复核完整15字段、严格整数非负版本，再立即带该版本单次CAS。现场版本检查放在预览前，不在取得最终版本后插入其他网络读取。若再遇409，保留失败、只读核对原字段，不盲目重交；重复项的主项绑定仍另按原合同核实。此方法不改变服务器权限或并发保护。

- 部分成功时，按原收据的真实逐项终态子集计数，不等整批`completed=true`才登记。若执行器已返回完整post-CAS队列且会话已撤销，复用该快照与counts核对；现有`bind-existing-closure-snapshot.ps1`只生成离线快照绑定，明确区分“队列读取完成”和“源关单仍partial”，不补造原成功、不再次登录拉队列。409只针对未成功项检查新快照的原15字段；完全未变且原有有界续办授权有效时，派生单项新提案/新会话/新preview，保留旧失败，成功项绝不重交；状态或原文有变则单独挂起。
- 写入前取消同样只挂本项、不阻止其他真实成功项入账：当前原执行器在真实CAS前先持久化`writeAttempts=1`及`expectedVersion/idempotencyKey`；只有数值零写、精确`TaskCanceledException`、未完成回执且六CAS/结果标记全缺时，公共reader才可略过该项而不计成功。计数、撤会话、唯一ID、原单CAS/字段保留及精确409守卫不变；write1不确定结果、未知错误或伪成功继续拒绝。该分类依赖写前哨兵顺序，执行器若改变此顺序须同步更新合同，不能孤立复用。

## 当前问题确需原记录时，按需复用

用户于2026-10-16持续授权Bug取证：按具体报告及其明确关联对局，复用现有管理权限提取必要诊断、检查点和故障附近命令，不再逐场重复询问。可能含私牌或个人牌库的材料仅在本地隔离处理，优先加密落盘，不展示、分享或进入公共夹具；正常登录与读取审计保留。此授权不包括无关对局、全库导出、业务数据写入、扩大可见性、部署或关闭未验证反馈。

- 固定原报告顶层 `matchId`、房间、时间、客户端／服务端／引擎版本及故障 `revision/commandSequence`，交叉核对诊断绑定；房间号可能复用，诊断摘要不等于完整检查点。
- 在既有取证授权和隐私边界内，先读 `/api/admin/matches/{matchId}` 元信息，再用已有 `/replay?limit=50` 和服务端返回的 opaque cursor 有界推进到故障附近；不导出全库、不绕过字节或命令数上限。活动非沙盒不属于已结束回放查询范围，接口404不能单独证明记录不存在；分别记录待提取、活动态、410载荷过期、409版本不兼容、413读取边界。
- 用对应原引擎、卡池、随机状态和记录时间，从合法检查点重放故障前后命令；保留 Accepted、revision、hash 校验和首个差异序号，不用新版规则反算旧结果。核实际操作方、`pendingDefense`、堆叠、Prompt、确认和区域变化；Defense中无堆叠／通用Prompt既不能单独判死锁，也不能单独判正常。
- 正常管理接口失败时，不反复从头重建分页，也不把失败当成载荷不存在。仅在已有只读取证权限内，允许按同一精确对局绑定、只读一致性事务提取最近检查点及故障邻近命令，限定时间/字节并加密；不导出全库，不借此绕过认证或扩大可见性。原版本与随机状态/逐步哈希仍须严格验证；409不兼容和410过期分别记实，不能以新规则强算或伪称原局通过。
- 权威流程通过后才转真实页面消费者：先证明合法接收者快照已到实际组件，再验可见、裁切、遮挡、禁用和原生点击／发送／确认；保持同实例生命周期，不用重新挂载掩盖问题。引擎通过不等于UI通过，相关合成场景不等于原玩家记录复现。
- 每条需要取证的事项只保留一个结论：原记录复现、权威通过但UI待查、相关合成、实际确认载荷缺失／过期、版本不兼容或尚未提取，附输入SHA、版本、序号及边界后再进入既有关单流程。当前问题确需原记录时，不因描述短跳过已有记录，也不问用户是否记得玩家场景；符合上方当前版本旧反馈收口规则的，不重复追溯，有效同源证据继续复用。
- 私牌、账号、令牌和真实房间秘密不得进入普通反馈、共享夹具或聊天。新增取证权限或产品裁定只挂起该项，不中断其他清单；此流程本身不授权扩大提取、改留存策略或关闭未验证Bug。

## 开发电脑只读拉取

密码只从 `L12_ADMIN_PASSWORD` 环境变量或交互式安全输入读取，不写入仓库：

```powershell
$env:L12_ADMIN_PASSWORD = '<服务器管理员密码>'
powershell -ExecutionPolicy Bypass -File .\ops\windows\Get-L12BugQueue.ps1 -Status new -OutputPath D:\GPT\L12-bug-queue.json
```

可用筛选参数：`-Status`、`-Priority`、`-Search`。脚本只调用登录和 Bug 查询接口，不包含更新、关闭或删除操作。

## 管理后台闭环

- 检索：编号、标题、正文、玩家、页面、房间、对局、负责人。
- 筛选：状态与优先级。
- 关联：存在 `matchId` 时可直接打开对应对局 JSON。
- 审计：建立反馈、状态、优先级、负责人、处理摘要和追加记录均持久化。
- 历史数据：旧 Bug 没有时间线时仍可读取；第一次处理后开始保留完整历史。
