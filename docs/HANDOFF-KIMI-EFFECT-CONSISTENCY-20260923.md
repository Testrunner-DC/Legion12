## 3. 第一批：建立可自动计算的生命周期完成矩阵

这是本轮唯一必须实施完成的批次。先完成并交回 Main 验收，不把 P1 运行时改造混入同一个差异。

### 3.1 目标

基于现有精确能力 ID、`L12LifecycleProfile` 和具名测试证据，生成机器可读且可审计的完成矩阵。它要回答：

- 生命周期档案总数与已完成档案数；
- 每个档案绑定的精确能力段；
- 每个档案适用的最低异常项；
- 每个异常项是“已有具名证据”“缺失”还是“明确不适用”；
- 每个缺失项对应哪些能力段和建议补测范围；
- 展示消费者是否覆盖按钮、选择/响应弹框、动效、日志、战报与回放。

最低矩阵项：

1. 正常结算；
2. 无目标/不能发动；
3. 已支付后被无效；
4. 已声明对象逆结算失效；
5. 重复或过期提交；
6. Prompt/堆叠/选择阶段重连；
7. 有费用时的取消/支付失败兜底；
8. 有对象选择时的唯一候选仍选择；
9. 多目标协议的部分失效继续；
10. 展示消费者覆盖。

### 3.2 真实性要求

- 不能因测试方法名称、源代码引用或“某张卡已有测试”就标为完成；必须由精确能力 ID 绑定的具名 evidence scope 支撑。
- `NotApplicable` 必须有具体原因；不能用“不适用”批量消除缺口。
- 同卡同触发的其他能力不能继承本能力证据。
- 档案归属、运行入口和测试证据是三件事；矩阵要分别展示。
- 生成器必须确定性输出，重复运行内容一致。
- 不得为了提高完成率而降低退出条件；如现有证据不足，应如实列为缺失。
- “玩家战报不显示内部结果类型”属于呈现策略，不等于服务端可以合并 `declined/noop/failed/negated/cancelled`。

## 4. 第一批验收后续队列

只有 Main 接收第一批后，才继续下面的一个有界 P1 家族；不要提前把全库 `effect-cancelled` 机械替换。

### P1 首批：结果语义审计与共享出口

目标语义：

- 资格阶段不允许发动：返回明确拒绝，不建立效果声明；
- 玩家选择不发动：`effect-declined`；
- 必发但无对象/无事可做：`effect-noop`；
- 已声明后来源、对象或条件失效：`effect-failed`；
- 响应成功使效果无效：`effect-negated`；
- 只有真正的事务取消才使用 `effect-cancelled`。

执行方法：

1. 全库扫描五类结果事件的生产者和消费者；
2. 按真实语义分组，先选一个共享根因、范围可封闭的家族；
3. 用失败回归证明误分类，再修改共享结果出口；
4. 覆盖所有命中的同族卡，不做单卡补丁；
5. 保留 GM/审计/测试层的结果区别；玩家战报可以按既有展示策略隐藏内部类型；
6. 交回 Main 验收后再进入下一家族。

## 5. 卡效通用规则（不得自行更改）

- 生命周期顺序：`资格 → 候选 → 选择 → 支付 → 响应 → 结算复验 → 状态更新 → 事件/动效/日志 → 重连恢复`。
- 冒号前是 Cost/发动条件；费用入栈前支付，后续被无效或目标失效不退款。
- 对象选择即使只有一个合法对象，仍由玩家点击；纯资源费用可例外。
- 已声明对象失效时不换对象、不补位；多目标只有协议明确为独立结算时才允许其余目标继续。
- 卡文没有次数限制时不得擅自增加；点名卡名的次数限制按同名共享特例处理。
- 没写“至多/最多”的固定数量必须足额，不足则整段不执行该回库效果。
- 无触发的天灾也遵守“天灾不触发任何效果”的既有裁定；不要重新打开已关闭边界。
- 芬尼亚传奇本次既有裁定只改变其“触发”部分，“我方回合 1 次”能力保持不变。

如发现规则文本与当前裁定冲突，停止该项并列出：卡号、原文、当前实现、冲突点、两种以上可选裁定及影响范围。不要代替用户裁定。
