# 卡效统一出口：集成门槛与架构准备

状态：准备完成，等待卡效专项收口后执行集成。本文不改变任何卡牌、对局规则或生产环境。

基线：`29212fc`（2026-09-17 读取时的 `origin/main`）；线上仍是已发布的 `815771d`。后续验收必须以实际准备合入和发布的提交为准，不能复用本文记录的旧测试结果。

## 目标

将每张卡的玩家可见效果统一收束为一条可审计的路径：卡牌能力的稳定身份决定运行时结算入口；结算只写权威状态；权威状态变化再产生面向玩家、回放和后台的一致结果。这里的“统一”不意味着把所有卡牌硬塞进同一个大函数，而是让同一类语义共享一个规格和生命周期，复杂组合效果继续保留明确的组合流程。

当前专项已经建立了这条路径的关键组成：

```text
卡牌数据 / 人工审定
  → L12AtomicEffectCatalog（能力、原子、稳定 AbilityId）
  → L12RuntimeEffectRoutes（卡号 + 时点 → 语义流程）
  → 原子解释器或已验证的组合流程
  → L12GameEngine 的 Prompt / 堆叠 / 权威事件 / 状态变更
  → 带 AbilityId、SceneId、段与结果状态的对局事件
  → WebSocket 快照与前端日志、动效、回放、后台展示
```

现有 `AbilityId` 由卡号、时点、执行模型、原子顺序和参数生成，不依赖后台排序；`SceneId` 从该能力身份派生。`L12RuntimeEffectRoutes` 已是后台、实战与回放的共用入口，不能为某个消费者另开卡号判断或仅前端解释的效果分支。

## 不可破坏的集成约束

1. 服务端 `L12GameEngine` 是唯一能提交对局状态的权威；前端、后台和回放不重新执行卡效。
2. 每个可运行能力必须有稳定 `AbilityId`，每段玩家展示必须有稳定 `SceneId`；不得按数组序号、显示顺序或中文文案定位。
3. 一条运行时效果只允许一个语义流程拥有结算权。旧分支只能作为明确标注的在途状态兼容，不能成为新卡或新功能的常规入口。
4. 冒号前真实支付、选择、响应、结算复核和结果必须仍属于同一事务。不能因抽取模块而提前结算、重复扣费或跳过逆序复核。
5. 触发来源是权威事实而非卡名猜测。尤其天灾“阶段自然增长”与“打出天灾军团／使用卡牌”必须分别携带来源、次数、响应和展示语义。
6. `resolved`、`negated`、`failed`、`declined`、`skipped` 等结果只由实际结算产生；展示层不可用文案推断结果状态。
7. 私密候选、已冻结支付事实和快照恢复边界不得因新增日志/动效而泄露或重新计算；恢复与重复提交至多结算一次。
8. 玩家文案是权威结果的投影，而不是规则输入。更新日志、对局日志、动效和后台审查可以共用身份与结果，但各自可有适合受众的文本。
9. 新的基础设施先围绕上述边界抽取端口，不重写已通过回归的卡效语义；一次只迁移一种完整结算形态并做全池扫描。

## 后续集成顺序

### 阶段 A：收口卡效专项（当前优先级 P0）

等待正在进行的“天灾触发来源分离”和后续统一卡效批次完成。每批须提供：完整命中清单、明确排除项、旧入口删除/兼容说明、针对取消/无效/目标失效/恢复/重复提交的回归证据，以及最终提交的全量原子审计结果。

本阶段禁止为了“架构整洁”拆分 `L12GameEngine`、更换协议字段或改写存档格式。

### 阶段 B：冻结出口契约（卡效批次收口后）

在不改变行为的前提下，为下列边界补齐可直接断言的契约测试和数据夹具：

| 边界 | 固定内容 | 不允许的变化 |
| --- | --- | --- |
| 能力目录 | `AbilityId`、结构哈希、时点、原子、迁移/审定状态 | 仅因后台重排或改文案改变身份 |
| 运行时路由 | 卡号、时点、语义流程、唯一结算所有者 | 新增逐卡旁路或双重结算 |
| 事务生命周期 | 候选、选择、已支付成本、响应、复核、结果 | 提前支付、二次支付、无效后执行 |
| 结果投影 | `SceneId`、段/分支、结果状态、公开范围 | 用文本或前端状态反推规则 |
| 快照/回放 | 已冻结事实、一次性结果、协议版本 | 恢复时重新抽取候选或再次结算 |

### 阶段 C：只抽取端口，不移动语义

先从 `L12GameEngine` 周边抽取纯读取或明确写入端口，例如：能力目录查询、运行时路由解析、事件投影、快照编码和后台审计查询。核心仍由同一原子对局事务持有，直到这些端口能以相同夹具获得完全相同的状态、事件序列和玩家可见结果。

仅在阶段 C 的差异通过后，才评估把房间、WebSocket、持久化和分析投影逐步移到外围；不可将网络断线、数据库故障或后台查询直接带入规则结算路径。

## 合入与发布门槛

1. 以 `origin/main` 的最新提交创建或快进集成工作树，先确认没有未提交的另一工作流差异；不同物理工作树中的文件不视为已同步。
2. 对照本批完整卡池命中/排除矩阵，审查每条路由只有一个结算所有者，并核查所有新增/移除的 `AbilityId`、`SceneId` 和旧兼容入口。
3. 运行该批专项、全量原子审计和提交级规则验证；涉及前端事件字段时，加跑连接恢复、UI 契约与生产构建。测试结果必须绑定最终候选提交。
4. 只有以上门槛均通过，才由主任务整合、提交和推送。部署仍需该部署批次的明确用户授权。
5. 如实际部署，玩家更新日志只描述玩家侧卡效、对局逻辑和页面变化；不公开后台审计、协作、存储、内部路由或安全细节。

## 协作边界

- 卡效专项拥有规则语义、卡效规格、对应回归和全池矩阵；其他工作不得同时修改这些文件。
- 主任务拥有合并、最终验证、任务台账、发布记录和部署；任何工作流的上下文、临时文件或未提交差异都不视为自动同步。
- 本文只定义“何时可接手”的客观门槛。卡效专项尚未给出最终回归回执前，架构工作只能进行文档、夹具目录和只读审查，不能实施规则内核重构。
