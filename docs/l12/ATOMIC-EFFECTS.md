# 卡效原子化架构

更新日期：2026-08-23

## 目标与边界

卡效原子化用于把卡面上的一个能力拆成可审计的“时机、条件、选择、费用、结算、期限、可见性”序列。后台展示和实战执行必须读取同一份定义，禁止维护一套仅供画流程图的影子配置。

当前 248 张 S1/S2 卡均已进入原子清单。无法证明与旧实现等价的能力会显式带有 `legacy.resolve`，继续由旧权威分支结算；只有 `verified-runtime-program` 能标记为“实战已验证”。这两种路径互斥，不能在一次结算中同时运行。

## 状态含义

| 状态 | 含义 |
| --- | --- |
| `legacy-backed` | 尚未形成可执行原子序列，全部由旧权威分支处理 |
| `partially-atomized` | 已拆出部分原子，但仍存在旧实现兜底，或同卡其他能力尚未迁移 |
| `declarative-ready` | 文本已能完整描述为原子，但尚未完成实战等价回归 |
| `verified` | 后台和实战共用同一份原子程序，旧分支已删除，并有回归测试 |

迁移状态只回答“实战是否已经由原子程序接管”。人工审查单独使用以下状态，二者不可互相推导：

| 人工审查状态 | 含义 |
| --- | --- |
| `unreviewed` | 自动整理，尚无人工作出卡面语义确认 |
| `human-assisted` | 已按设计者提供的拆分思路整理，仍待逐项确认 |
| `confirmed` | 设计者已明确确认该卡的能力边界 |

因此，一项能力可以同时是“人工确认”与“部分原子化”：前者说明语义边界已经确认，后者说明实战暂时仍由旧权威分支结算。后台必须同时展示两种状态。

## 人工辅助拆分准则

1. 以一次可独立进入规则时点的能力作为能力边界，不按句号或换行机械切割；同一段文字若包含“登场时”和“进攻时”，应拆成两个可执行能力。
2. 每项能力内部按 `condition → cost → target → resolution → duration → visibility` 排列原子；没有的阶段不造空节点。
3. 【强攻】【免死】【必中】【挑衅】【冲锋】【隐匿】【震击】【贯穿】只引用 [`RULEBOOK-KEYWORDS.md`](./RULEBOOK-KEYWORDS.md) 的公共定义；卡牌不得复制另一套规则正文，后台可展开公共定义供审计。
4. 展示属于公开信息策略：必须记录双方可见、对手确认以及日志中的可查询卡名；它不应被误建模为弃置或移区。
5. 【晋升】是独立的特殊登场流程；普通登场与晋升登场若各有触发，必须分别建立时点，不能因文字相邻而合并。
6. “位于前排/后排”“位于手牌”等条件应进入派生查询；客户端按钮、距离、费用与后台原子不得各自按卡号复制判断。

奥林匹斯人工辅助现已覆盖 S02-0501 至 S02-0523 的已提供能力，以及 S02-05M1〈阿尔忒弥斯〉。其中 S02-0502〈赫拉克勒斯〉、S02-0506〈珀尔修斯〉、S02-0521〈荣耀之路〉、S02-05M2〈普罗米修斯〉、S02-05C1〈神力〉与 S02-05C1A〈士气〉标记为人工确认；其余已由设计者给出拆分思路的卡标记为人工辅助。该标记只确认能力边界与原子组合，不代表实战旧分支已删除。

## 单一事实来源

- `AtomicEffects.cs`：原子注册表、全卡映射、覆盖率和已验证程序。
- `L12AtomicRuntimeIntegration.cs`：只执行已验证程序，并调用现有规则内核操作。
- `Data/effects/atoms.schema.json`：可持久化定义的 JSON Schema。
- 管理后台“卡效原子化”：查看原文、能力拆分、参数、流程图、迁移状态和原始 JSON。
- `ATOMIC-EFFECT-BASELINE.json` 与 `scripts/audit-l12-atomic-effects.ps1`：阻止卡池漏图和旧分支数量反向增长。

## 迁移门槛

一个能力只有同时满足以下条件才能成为 `verified`：

1. 按正确规则时点拆分，冒号前费用、目标、可选性和期限均有独立原子。
2. 所有原子均由服务端权威内核执行，客户端只提交选择意图。
3. 原子程序与后台展示来自同一对象。
4. 删除对应旧分支，保证一次效果只结算一次。
5. 覆盖正常、拒绝、目标失效、费用不足、空牌库及隐藏信息等适用边界。
6. 全量测试和原子化审计通过，随后下调旧分支基线形成棘轮。

## 首批实战迁移

实战只把无交互或已完成等价回归的能力接入 `verified-runtime-program`。验证程序数量必须从 `L12VerifiedAtomicPrograms.All` 与审计测试派生，不能在文档中手工维护另一套容易过期的统计。后台可查看的结构化能力、人工确认和 `declarative-ready` 都不等于旧实战分支已经删除。含“可”的抽牌/抽弃等交互能力必须经过公共 Prompt 运行时，禁止把可选效果降格为无条件原子。

后续按“静态/派生数值 → 标准触发/主动 → 目标与费用 → 复杂 Prompt/Stack → 阵营、主宰、天灾、试炼与特殊区域”推进，不用关键词推断直接替代规则实现。
