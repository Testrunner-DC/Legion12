## 三、根因（读码定位，未改）

**D1 服务端：本桌帧的投递校验把通配收件人当成账号**
`服务端WebSocket/TwelveLegions/L12WebSocketServer.Chat.cs:120` 的 `FreshChatDelivery` 对除 Control 以外的所有帧先做
`_platform.ReadCommittedChatPair(metadata.SenderAccountId, metadata.RecipientAccountId)`，要求 `Available/BothAccountsActive/Unblocked`。
本桌的 `chatAck` 与 `chatHistory` 由 `L12ChatRuntime.cs:478/518` 以 `recipientId = work.PeerAccountId = "*"`（`TableBroadcastPeer`, `L12ChatRuntime.cs:873`）发出，拿 `"*"` 去查账号对必然不成立 → 帧被静默丢弃。这解释了「发送结果未确认」和「列表空」，也解释了为什么没有失败回执（失败回执同样走这条闸门）。

**D2 前端：收到的本桌消息记到另一条线程键**
`opcgpro-vue/src/l12/chatResource.ts:21` 的 `chatKey = [scope, peerAccountId, matchId]`；`entryConversation()`（同文件 159 行）对收到的条目按 `senderId` 反推 peer，于是 B 收到的条目 peer=A，而 B 打开的本桌线程 peer 是 `"*"`（`SocialPopover.vue:61`）。`merge`（162 行）比对 key 不等即跳过，消息被记到一条永不渲染的线程里。

**为什么单测是绿的**：`TwelveLegions.Platform.Tests/TableChatScopeTests.cs:122` 的 `BroadcastMessageReachesEveryOtherTableMember` 用「对方账号 id」当 peer，走的是 opponent 分支；线上 UI 用的是 `"*"` 广播分支，`FreshChatDelivery` 根本不在该测试的覆盖范围。

## 四、建议的修法（待授权）

1. D1：`FreshChatDelivery` 遇到 `Scope == Table && RecipientAccountId == "*"` 时改判「发送者是本桌成员且连接代次匹配」，不再走账号对查询；逐个成员扇出的帧仍按成员对校验。
