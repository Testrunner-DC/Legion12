# 十二军团 · 卡牌效果实现说明（编辑 / PM 版）

> 适用对象：负责卡牌数据录入、新卡效撰写的项目成员（非工程师）。
> 目的：说明"卡面文字"如何变成"引擎里真正会发生的效果"，以及怎么自查一张卡有没有写对。

## 1. 卡效写在哪、怎么分四类

每张卡的效果不在 `cards.ts`（那里只存卡面原文 / 费用 / 阵营等元数据），而是按"触发方式"注册到引擎的四个表：

| 注册表 | 含义 | 谁发动 | 典型例子 |
|---|---|---|---|
| `CARD_EFFECTS[卡id][钩子]` | 被动触发（登场 / 进攻 / 阵亡 / 抽牌…） | 引擎自动在对应时机调 | 吕布登场进攻无损、张飞挑衅 |
| `ACTIVE_ABILITIES[卡id]` | 主动式（主动休整 / 消耗士气） | **玩家按按钮** | 凌霄宝殿击杀、众神之乡检索 |
| `COST_REDUCTION[卡id]` | 静态费用减免 | 引擎自动查 | 张飞 / 韩信（我方士气低时登场费-1） |
| `REACTION_HANDLERS[卡id]` | 反应式（对方进攻时 / 发动效果时） | 引擎在对应时机触发一次 | 伏击、战斗至黎明 |
| `MASTER_ABILITIES` / `FACTION_ABILITIES` | 主宰能力 / 阵营效果 | 玩家按按钮 | 杨戬抽牌、天廷阵营追加士气 |

> 天灾牌（S01-DSxx）不逐张注册，统一在引擎 `resolveDisaster` 按天灾值处理。

## 2. 「选择 / 可 / 可以」一律交还给玩家

卡面出现"选择""可消耗X士气""可返还X士气"等字样时，**引擎不会替玩家决定目标**，而是：
1. 把选择请求挂起（`eng.askUnits / askCards / askMode / askYesNo / askDiscard`）；
2. 对战界面（`Battle.tsx`）弹出对应选择弹窗，玩家点选后效果才继续；
3. 无界面环境（自动对战 / 压测）由兜底逻辑自动代答，**保证不卡死**，但那只用于测试。

编写新卡效时，**凡是卡面有"选择/可"的，都必须走 `eng.ask*`**，绝不能写 `field.flat().find(...)` 直接挑第一个——那会被审计标记为"想当然自动选择"（实现方式错误）。

## 3. 怎么自查一张卡写对了（三层审计）

项目内置审计，分三档，结果都落盘到 `scripts/*.json`，网页端 `/audit` 可看汇总：

| 审计 | 查什么 | 命令 |
|---|---|---|
| 覆盖审计 | 哪些卡已接入引擎、哪些缺口 | `node scripts/_audit.cjs` |
| 语义比对 | 卡面动词 vs 实现调用的 API 是否对得上（含"近似"标注） | `node scripts/_semantic.cjs` |
| 正确性 | 哪些卡"实现方式不对"（该玩家选的被自动选了） | `node scripts/_audit_correctness.cjs` |
| 单元 / 压测 | 强制跑全部卡效有无崩溃、300 局对战是否稳定 | `node scripts/_exercise.cjs` |

当前状态（2026-08-13）：覆盖 128/133 已接入、**0 逻辑缺口**；正确性 **0 张实现方式错误**；语义比对 23 处可疑 + 29 处"近似/简化"标注（属已知近似，非错误）。

## 4. 已知近似 / 简化（非错误，仅说明实现取舍）

语义审计标"近似"的卡多为"效果需复杂 UI 交互，当前用合理默认替代"，例如：
- 陵墓守卫相关多张的"代替承受 / 免死"用近似实现；
- 自伤换费用减免（传奇的拉格纳等）默认支付 1 点自伤；
- 部分"逐张自选顺序放回牌库"用保持原序的确定性默认。
完整清单见 `scripts/semantic-report.json` 的 approx 段。如需某张做到 100% 还原，单独提需求。

## 6. 给编辑的写卡效 checklist

1. 卡面"选择/可" → 必须走 `eng.ask*`（找工程师登记，不要硬编码挑目标）。
2. 费用 / 兵力 / 天灾等级等数值 → 与 `cards.ts` 字段一致。
3. "本回合"类限制 → 交给引擎 round 戳处理，不要写永久标记。
4. 新增能力后跑一遍第 3 节审计，确认不新增缺口 / 不新增"实现方式错误"。
