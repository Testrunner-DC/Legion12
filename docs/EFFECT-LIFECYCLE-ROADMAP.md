## 质量审查

### 已达到的质量

- 自动台账覆盖 324 张卡和 681 个能力段，不允许无能力卡或同卡同触发能力静默消失。
- 能力使用稳定 ID 和结构哈希；共享档案绑定精确能力，不能因同卡、同触发或相似文字误继承。
- 台账明确区分“定义/归属证据”和“完整执行回执”，不会把文件存在或测试名称当成生命周期完成。
- 当前主线提交级 Release 已通过：规则 **4499/4499**、平台 **138/138**、UI 契约 **331** 项、生命周期台账 **17/17**、卡图 324 张及生产构建；失败 0、跳过 0、退出码 0。
- 最近上线的五项统一批次已通过线上健康验证；维护模式已关闭。

### 仍需警惕的问题

- **台账归属不等于效果完成。** 401 个共享归属之外，279 个细定义/复合定义仍需按完整生命周期证明；即使已有运行入口，也不能直接视为验收通过。
- **测试总数不能表示矩阵覆盖率。** 当前具名证据很多，但尚未自动计算每个生命周期档案的正例、无目标、无效、目标失效、重复提交和重连是否全部齐全。
- **结果语义仍未完全统一。** 服务端仍有大量历史 `effect-cancelled` 写法，其中部分实际表达目标失效或结算失败，需要逐项分类，不能批量改名。
- **展示仍存在多来源。** 卡文和部分范围已经结构化，但按钮、弹框、日志、动效和回放尚未全部从实际能力段/分支投影。
- **文档与发布状态必须分开。** “进入主线”“Release 通过”“已部署”“维护已解除”是四个不同状态，不再在同一批次描述中混用。

## 下一步执行队列

除规则裁定、新权限或真实外部阻塞外，以下队列连续执行；Focused、Batch、Release、提交和记录只是检查点，不是停止条件。

### 1. 建立可自动计算的完成矩阵

为每个生命周期档案生成下列状态，不再依赖人工百分比：

- 精确能力段和运行入口；
- 正常结算；
- 无目标/不能发动；
- 已支付后被无效；
- 已声明对象在逆结算后失效；
- 重复或过期提交；
- Prompt/堆叠/选择阶段重连；
- 费用取消、唯一候选选择、多目标部分失效等附加项；
- 展示消费者：按钮、弹框、动效、日志、战报、回放。

输出应直接给出“已完成档案数 / 总档案数”和缺失项列表；路线图的完成度以后由该矩阵更新。

### 2. P1 结果语义统一

按真实语义审计旧结果出口：

- 不能发动：资格阶段拒绝，不建立效果声明；
- 选择不发动：`effect-declined`；
- 无对象或必发但无事可做：`effect-noop`；
- 已声明后对象/来源/条件失效：`effect-failed`；
- 响应成功无效：`effect-negated`；
- 仅真正的事务取消保留 `effect-cancelled`。

验收：同一结果只由一个公共出口产生；服务端事实、GM/审计和测试可区分；玩家战报可按展示策略隐藏技术结果，但不得改变底层事实。

### 3. P2 剩余对象族

依据完成矩阵，按“区域 + 对象协议”分族，不按单卡修补：

1. 私有区已声明对象：手牌、墓地、牌库；
2. 公开区类型变化：临时成为军团、主宰/圣物离开临时形态；
3. 单目标、独立多目标、固定数量和“至多”数量；
4. 目标替换、占位失败、来源失效和不得补位；
5. 唯一合法对象仍必须由玩家点击的入口。

每族必须同批完成代码、具名测试、台账和记录。

### 4. P3—P4 费用与触发族

- 费用：士气、临时士气、神力、符文、弃牌、自伤、返还、墓地代表值和复合费用。
- 触发：登场、阵亡/离场、进攻/击杀、主动、反击、试炼/符文、天灾、多段分支。
- 统一冒号边界、支付时点、响应范围、次数身份和“随后”依赖；卡文未写次数限制时不得擅自添加。

### 5. P5 展示同源

每个效果段提供同一份结构化来源：卡牌/实例、段 ID、时点、必发/选发、Cost、候选、目标、响应范围、分支、实际结果、公开等级和版本。

图鉴、按钮、选择弹框、响应弹框、动效、日志、战报和回放只做对应视角的投影，不各自维护规则或文案。

### 6. P6 最终验收与部署

- 每个生命周期档案通过最低异常矩阵；
- 全卡台账无未归属项，或保留项具有明确裁定、负责人和目标版本；
- 使用保存的状态/回放夹具完成最终回归；
- 完整规则、平台、UI、连接恢复、卡图、生产构建和发布包全部通过；
- 部署后核验 HTTP、WebSocket、版本、卡图、服务重启次数和维护状态。

## 执行纪律

- 同族扫描、修复、具名测试、Batch、记录和提交必须同批完成，不为单个入口重复跑完整发布验证。
- 只在最终退出码和汇总核实后登记通过；进程启动或部分输出不能计作成功。
- 保留其他任务的工作区修改，不整库覆盖、重置或清理无关差异。
- 新卡或改卡必须先绑定既有生命周期档案；确实无法表达时新增共享协议，不为单卡复制一套流程。
- 卡效后台工作台安排在 P0—P6 完成后：届时再开放效果、勘误、产品、弹框/日志和带图例呈现样式的结构化编辑与发布。

## 完成标准

只有以下条件全部满足，才能标记“效果一致性完成”：

1. 324 张卡的全部能力段均有生命周期档案、运行入口和具名证据；
2. P0—P6 全部退出，未处理清单为零或具有明确产品裁定和目标版本；
3. 不能发动、拒绝、跳过、失败、无效和取消在服务端事实中可区分；
4. 按钮、弹框、动效、日志、战报和回放读取同一能力段及实际分支；
5. 每个生命周期档案通过最低异常矩阵；
6. 完整发布门禁和线上部署验收通过。

在此之前，只能声明某个阶段或某个生命周期族完成，不能笼统宣称整个效果一致性完成。

## 效果一致性完成后的路线：后台卡效工作台

目标：维护者能够在后台完成卡牌规则和呈现配置，不再依赖逐条对话修改代码。

统一维护的内容：

- 卡牌基础资料、所属产品、收录产品、版本和生效范围；
- 按“卡牌 → 能力 → 效果段”拆分的时点、必发/选发、冒号前 Cost、候选、目标、响应、分支和结算；
- 勘误原文、新文、原因、生效版本、影响产品、历史修订和回退记录；
- 按钮、发动/支付/选择/响应弹框、动效、日志、战报和回放文本；
- 每种呈现样式的名称、适用场景、公开等级、参数和桌面/移动端预览。

呈现样式选项必须附带静态图例或可播放范例，不能只显示内部枚举名称。后台复用统一设计系统，按钮、间距、弹框、表单、错误状态和响应式布局不得为单个功能临时拼接。

发布流程固定为：

`草稿 → 结构校验 → 场景预演 → 人工复核 → 差异确认 → 发布 → 审计/回退`

已发布版本不可原地覆盖；进行中对局、录像和日志绑定冻结的规则与展示版本。无法用现有结构表达的规则进入“待开发”，不得以自由文本冒充已接入运行时。

完成标准：维护者可在后台配置 Cost、目标、响应、分支、卡文、勘误、产品和带图例的呈现样式，并同时预览图鉴、按钮、弹框、动效、日志和回放；一次审核发布生成同一版本的运行定义与全部界面投影。
