# 十二军团架构目标

状态：长期目标与决策索引。本文记录已经讨论确认的方向，不授权立即重构、同步或部署。每个阶段仍须在开始前取得相应的用户确认，并以当时的最终候选提交重新验证。

当前基线：线上版本为`815771d`；卡效统一工作以最终合入的`origin/main`为准。不同工作树、任务上下文和未提交文件不会自动同步。

## 一、北极星

十二军团保持**服务端权威、单局原子结算、客户端只投影状态**：

```text
玩家命令
  → 合法性与费用/选择校验
  → 单局效果堆叠、Prompt 与权威状态事务
  → 权威事件与结果状态
  → 快照、对局记录、动画、回放、后台审查的受限投影
```

卡效的唯一出口为：

```text
卡牌/规则资料 → 稳定能力身份与原子目录 → 运行时路由
→ 原子解释器或已验证组合流程 → 权威结算 → 玩家可见结果
```

详细的卡效出口约束与合入门槛见[卡效统一出口集成门槛](CARD-EFFECT-OUTLET-INTEGRATION-GATE.md)。本文件不取代该文档。

## 二、架构原则（长期不变）

1. `L12GameEngine`是单局状态的唯一写入者；浏览器、后台、回放和分析不得重新计算或补执行卡效。
2. 卡牌能力、展示场景、结算结果与公开范围必须有稳定身份；不能以文案、显示顺序或前端临时状态作规则依据。
3. 一项效果只有一个结算所有者。允许复杂组合流程，但禁止新增逐卡旁路、双重结算或前端规则副本。
4. 命令、支付、选择、响应、逆序复核、结果与恢复属于同一事务；断线、重复请求或旧 Prompt 均不得二次结算。
5. 隐藏信息按接收者投影。对手、观战者、后台审查和回放分别拥有明确可见范围，不能从日志、动画或错误提示反推出私密信息。
6. 内容规则与运营控制分层：卡牌、规则书、FAQ、禁限与赛事版本均可追溯，但运行中的对局固定其创建时的规则/运营版本。
7. 前端以领域状态和组件展示分层；网络恢复、快照核验、界面布局和业务规则不得相互偷渡职责。
8. 单体可模块化，但不以微服务化为目标。只有边界、失败模式、监控和回滚都清楚时才考虑进程或存储拆分。

## 三、目标模块边界

| 层级 | 当前核心 | 目标职责 | 不应承担 |
| --- | --- | --- | --- |
| 接入层 | `L12WebSocketServer` | HTTP/WS 连接、认证、协议版本、输入/输出编码、健康检查 | 具体卡牌规则、房间内状态改写 |
| 房间层 | `L12RoomManager` | 建房、入房、座位、匹配、重连绑定、观战权限与生命周期 | 结算卡效、推断对局结果 |
| 对局内核 | `L12GameEngine`及其局部模块 | 命令事务、效果堆叠、Prompt、权威事件、状态与胜负 | HTTP、数据库查询、UI 文案决策 |
| 卡效出口 | 原子目录、运行时路由、组合流程、展示场景 | 将能力身份映射为唯一结算流程与可审计结果 | 绕开内核直接改变状态 |
| 事件/快照层 | 对局事件、状态快照、连接恢复 | 版本化快照、序列、恢复、回放输入与接收者投影 | 通过重放日志猜测私密选择 |
| 持久化/分析层 | SQLite、档案、排行榜、单卡分析 | 写入已完成的权威事实；构建可再生的查询投影 | 参与实时结算或反向修改历史对局 |
| 客户端领域层 | `net.ts`、`platform.ts`、L12 页面/组件 | 连接恢复、状态消费、动作提交、页面与交互状态 | 决定命令合法性或卡效结果 |
| 规则内容层 | `officialRules`、FAQ、卡牌资料、规则中心 | 规则书、术语、FAQ、禁限、赛事规则和版本记录 | 让页面文字覆盖实战权威规则 |

## 四、实施顺序与退出门槛

### P0：统一卡效出口（进行中，最高优先级）

完成整池能力的唯一入口、明确的触发来源、稳定展示身份与全池审计。天灾的阶段自然增长与由卡牌造成的主动触发必须分别建模。完成前不得为“整洁”拆分内核、协议或存档。

退出门槛：全池命中/排除矩阵、旧入口处置说明、取消/无效/失效/恢复/重复提交回归、最终候选上的原子审计与规则验证。

### P1：冻结内核边界（P0 收口后）

为能力目录、路由、事务生命周期、结果投影、快照/回放建立稳定契约和确定性夹具。仅抽取纯读取或已明确写入的端口，保证相同夹具产生相同状态、事件序列和玩家可见结果。

退出门槛：接口契约测试、旧新输出逐项等价、没有新增卡牌旁路、连接恢复和隐藏信息检查通过。

### P2：分离接入、房间与内容投影（P1 后）

将 HTTP/WS 接入、房间生命周期、规则内容查询和后台查询从对局内核外围抽离。先保持同一进程和存储，验证调用方向只从外围进入内核、结果只从内核流向投影。

退出门槛：房间/断线重连/观战权限/协议版本的专项验证；对局内核不直接依赖 UI、HTTP 或分析查询；完整回归通过。

### P3：版本化事件与持久化演进（P2 后）

将已确认的权威结果以追加式对局事件保存，并保留可版本化快照用于快速恢复；排行榜、战报和单卡分析由该事实生成投影。先为新局启用，旧局保留只读兼容和可回滚迁移，不重写或伪造历史事实。

退出门槛：同局恢复/回放一致、协议和存储版本兼容、隐私投影审计、失败写入恢复、备份与回滚演练通过。

### P4：产品结构与移动端体验（可与 P1/P2 并行）

规则中心在同一页面内按子页提供核心规则、快速入门、术语与词条、FAQ、构筑与禁限、赛事规则和版本记录。对战、牌库编辑与沙盒按实际可视区比例选择逻辑横向画布和移动密度，不依赖设备身份或物理方向；旋转只作用于显式加入的路由画布及其弹框宿主，不影响冻结的桌面宽屏布局和其他页面。页面规则始终使用 L12 术语和权威资料。

退出门槛：规则内容有来源、版本与生效日期；移动端对局经目标视口、Prompt/支付/重连/隐藏信息测试，桌面基线无回归。

## 五、明确禁止的捷径

- 在 P0 完成前大拆`L12GameEngine`、替换 WebSocket 协议或迁移存档格式。
- 让前端、后台、FAQ 页面或分析任务执行/修正规则结果。
- 以卡名、自然语言匹配或展示文案充当新的实战路由。
- 用“已构建成功”代替规则、恢复、可访问性或视觉验收。
- 把外部同类游戏的术语、卡效、数值、裁定或 UI 直接复制到 L12。
- 因共享项目名而假定跨任务已同步；未提交差异与对话计划必须显式交接。

## 六、协作与集成目标

1. `D:\GPT\Legion12\app`作为规范工作区；隔离 worktree 只用于明确的变更批次。合入前以`origin/main`与实际工作区状态为准。
2. 每个并行工作流须记录：负责人、基线提交、可写文件、禁止文件、首个交付物、验证项与回传对象。一个文件同一时刻只有一个写入者。
3. L12-Main 负责需求裁定、集成、共享台账、最终验证、Git 同步、玩家更新日志和部署。专项任务只交付有边界的方案、差异和验证证据，完成后显式回传 Main。
4. 每次生产部署都以已验证候选为单位，玩家更新日志只说明玩家可见变化；部署必须取得该批次明确授权。
