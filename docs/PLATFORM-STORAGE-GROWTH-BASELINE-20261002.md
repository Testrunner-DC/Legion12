本次只用 D 盘合成数据测量当前 `L12PlatformStore`，没有读写线上玩家资料、没有部署，也没有改变平台事务、镜像或锁的实现。原始机读结果保存在 `D:\GPT\Legion12\artifacts\platform-growth\run-20261001T210005-cbf391005ad44c8e909f82421ff72b29\report.json`。测量时间为北京时间 2026-10-02 05:00；机器为 Windows 10、24 个逻辑处理器；基准源码 SHA256 为 `91B1263D0F3E8AB3A35D3912CB8E5865B8930F3C6C70F2AA19128F8D9F1550EE`。

## 方法与边界

- 三档合成账号／每账号个人牌库／公开牌库／赛事为 `10/2/5/2`、`50/4/20/10`、`150/8/60/30`。账号密码哈希来自本地种子，牌库及赛事由本地种子克隆；各档从独立数据库导入、运行和恢复。无正式服数据。
- 每档对成功登录、更新同一牌库、切换同一公开牌库点赞、后台同角色审计写入各预热一次并顺序测量 100 次。数值为进程内 store 调用耗时，不含 HTTP、网络、浏览器或构筑校验；后台样本不是权限入口端到端耗时。
- 锁等待另以 4 个线程各成功登录 25 次计量：基准在调用前获取与平台方法相同的 `_gate`，记录 `Monitor.Enter` 等待。它测的是此合成竞争场景的锁排队，不是线上等待分布。
- 镜像与 SQLite 字节为 100 次操作后的最终文件大小，不是累计磁盘写入量；SQLite WAL 本轮结束时为 0。恢复时间为再次构造 store 且确认个人牌库数量的耗时，不等于灾难恢复演练。
- `P99` 为 100 个样本中的第 99 个顺序统计量，仅作小样本基线，不应作为生产 SLA。各档四个维度同步增长，不能据此单独归因于牌库数量。

## 判断与下一步

同机合成矩阵中，更新牌库 P95 从 8.37 到 34.60 ms，后台写入 P95 从 9.89 到 39.59 ms，登录 P95 从 22.06 到 48.48 ms；这支持“全域快照与锁竞争值得进一步隔离测量”，但不足以证明线上瓶颈或应当改数据库。锁等待 P95 非单调、P99 波动较大，不能声称其随数据规模线性增长。恢复验证均成功。

下一批若要优化，应先在测试环境补逐语句数量与累计写入字节观测，再做账号、牌库、公开版本、赛事的单变量矩阵及真实并发预算。只有证据表明问题由全量写入造成，才考虑按变更对象持久化；现有事务、版本、镜像容错和回滚协议不得先行削弱。F1 本身不实施存储架构改造。
