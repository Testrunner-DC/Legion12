# Legion12 服务器存储维护方案

## 当前结论（2026-09-09；容量为 09-08 核验值）

- 正式 `matches.db` 约 41.8 GB。635 场旧 `storage_version=1` 对局保存每个命令后的完整 `state_json`，是历史占用主体。
- 新 `storage_version=2` 已改为增量命令日志、动作事件与 Brotli 检查点。最近 10,243 条 v2 命令的 `state_json` 合计 20,486 字节，平均 2 字节；最近检查点平均从约 415,858 字节压到约 16,578 字节，压缩约 96%。新对局不会再按动作线性复制完整状态。
- v2 回放以版本化规则程序、卡牌目录、初始检查点和最小命令参数重建固定动作；动作审计只保存卡号、实例号及当时的事件结果，不再为每次动作重复复制整张渲染卡牌。规则或卡牌文本必须按对局绑定版本读取，不能用当前目录改写旧局含义。
- 单卡分析仅分析新采样资格、真实卡效版本齐备的排位对局，不兼容或回填旧分析数据，不纳入休闲/好友房/沙盒。不持久化胜率、切片或图表缓存；列表统计缓存仅内存最多 32 项、30 秒，结算/匿名化使缓存失效。新排位终局按“对局 + 玩家 + 卡号”紧凑化；构筑只保留在 `match_deck_cards`，账号只保留在参赛方表。逐条事实保留 30 天供排障，之后删除明细但保留紧凑计数和覆盖质量。
- 测试服只承担前置验收，不作为长期玩家档案。日常发布只保留当前/上一程序、最新 1 份测试 runtime 快照和实际引用卡图；同哈希卡图可用只读硬链接复用物理数据块。

## 自动维护边界

### BATCH296 独立制品盘治理

09-09重新只读核验：根盘可用约4.49GB/93%；`/www`为独立vdb1、持久rw挂载，可用19,866,779,648字节。512场无关旧录像载荷已清理，391场保护；数据库约42.14GB物理文件不变，约17.64GB内部页可复用。以下外置发布方案的实际启用仍以最终部署回执为准。

- 新发布包、暂存、程序、备份与新哈希卡图只使用`/www/legion12`固定子目录；活动链接和运行数据库仍留在原路径。不把根分区停止新解包的门槛关掉，也不在根盘执行VACUUM。
- 两个分区分别监测容量，不能把外盘空闲当成数据库所在根盘空闲。上传前外盘至少14GiB；发布前预算为4GiB备份硬上限、实际解包大小与8GiB余量，任一检查失败停止。数据库增长继续优先复用已释放页；容量不足时应做明确维护方案，不静默迁库。
- 外置备份需要完整压缩流校验、SHA256及0600权限，未完成文件不算恢复点。外置模式本批不自动删备份，尤其不动原根盘两份快照；后续容量不足必须先列出真实恢复需求和精确清单，再按授权清理，不能靠滚动删除掩盖增长。
- 正式程序保留数跨`/opt/legion12-releases`与`/www/legion12/releases`合并统计为当前+最近5个可用回滚版本。当前和历史正式/测试程序实际引用的卡图全部保护；相同哈希优先复用已有缓存，不重复拷贝。
- 每次发布记录两个盘的前后可用字节、备份大小/哈希、实际活动目标、旧版本与测试版本；发生失败时保留新数据及诊断，不把旧快照自动覆盖回去。

2026-09-09 用户最新保留要求：正式服保留当前运行版本，另保留最近 5 个可用回滚程序版本及其实际引用资源。按已核验的部署记录排序，不按目录修改时间猜测；失败、不完整或数据不兼容的程序不能算作可用回滚点。不能为了凑足/削减数量删除 Bug 证据或仍被正式/测试服务引用的依赖。此数量不适用于持久化数据备份；测试服原隔离策略不因正式服清理自动改变。当前正式服为 1 个活动程序加 4 个历史程序，未超过该上限，无需删除历史程序。

1. 每次测试服发布成功后自动执行测试专属清理；失败发布不清理，以保留现场。
2. 测试 incoming 超过 2 天且未被发布使用的文件可删；正式 incoming、正式 runtime、正式快照和事故证据不由测试脚本处理。
3. 正式程序保留活动版本和最近 5 个可用回滚版本，关联资源同步保护；正式 runtime 快照保留策略必须在新快照通过校验后执行，绝不以旧快照覆盖已产生的新事实。
4. 根盘达到 85% 或剩余不足 8 GiB 时进入容量警戒；达到 92% 或剩余不足 5 GiB 时停止新的发布包解压和全量快照，先人工处置。数据库、WAL、服务重启次数与活动版本必须一并记录。
5. Nginx 日志继续交由 logrotate；systemd journal 建议封顶 128 MiB。APT 缓存可以重建，但不得把清缓存当作数据库容量治理。
6. 单卡事实维护正常每日运行：仅新有效排位赛果在终局事务内紧凑化；仅补齐新资格局的汇总，每轮最多25场。有效排位明细30天且已有汇总才清；不参与分析的已结束休闲/好友房/旧排位明细按用户09-09授权10天后直接清，不做无用回填。新非排位不再采集分析事实/版本，不生成空汇总标记；构筑与回放仍保存。每轮清理最多100场，触顶5分钟后续扫，消化积压后每日；不清active/sandbox、不执行启动全库聚合或生产即时清理。
7. 玩家回放入口固定最近 30 场（按结束时间、开始时间、match ID 稳定倒序；不含沙盒）。休闲/好友房录像只有退出双方各自最近 30 场集合后才可清理；排位也占玩家 30 场窗口，但排位后台录像不由此规则删除。每日小批维护，每轮最多 100 场，有积压则 5 分钟后续扫。
8. 回放清理保留 matches、参赛方、构筑、统计与命令摘要/条数；只释放初始状态、逐命令状态、v2 请求/事件/检查点载荷，并记录过期墓碑。后台摘要仍可查，回放请求明确 410，不尝试重建已删检查点。已不在本人窗口的直接 URL 也不可越界读取。
9. 活动对局、排位恢复/结算/隔离记录、未关闭或未解决 Bug 的 match ID/room code 引用均保护。每场删除前重新读取 Bug 引用；平台 JSON 与 SQLite 无共同事务，极短并发新建报告不能追溯恢复已删录像，Bug 自身最小诊断独立保留。不要把这项保护描述成无限期全量证据备份。

## 旧录像以清理为主（覆盖早先迁移建议）

用户明确不再投入旧 v1 转换、重放验证或兼容性开发。2026-09-09 用户进一步明确授权一次性清理与 Bug 无关的录像，不备份、也不要求仍可从玩家最近 30 场入口查看；截止严格为 2026-10-01 00:00 UTC+8 之前。新增范围仅为可重建缓存、临时文件和不再引用的旧产物；保留账号、构筑、战绩、排位结算、全部状态的 Bug 证据及活动/恢复/待结算/隔离记录。关联缺失不能当成无价值，需按报告者历史等保守保护；旧排位启动仍依赖录像的记录也保护。不得整库删除或把本次授权变成每日无条件删录像。实际删除以单独执行回执为准；此前八月份截止已被这次明确日期授权覆盖。

释放大文本首先形成 SQLite 内部空闲页，供后续写入复用，不保证文件立即缩小。若要缩小文件本身，须在维护窗口使用足够的机外/外部临时空间重建数据库，并校验完整性、外键、赛果行数和版本切换。当前根盘不允许原地 `VACUUM`，也不能把有容量上限的 WAL 留存配置误报为活跃 WAL 硬上限。

## 保留策略

- 正式排位：玩家仅最近 30 场；后台编码事件与必要检查点保留，不纳入休闲/好友房日常清理。
- 休闲/好友房：退出双方各自最近 30 场且无保护时每日清理录像，保留赛果与统计，不以录像清理替代账号数据治理。
- 单卡分析：仅新排位构筑快照和紧凑汇总长期保留；逐条卡牌事实保留 30 天。汇总不含账号、昵称、完整卡牌文本或可重新计算的图表结果；样本依赖与覆盖未知必须显式提示。
- 沙盒：录像保存 7 天，每周清理，因此实际保留约 7–14 天；玩家不可直接查看，但管理员可用于 Bug 溯源。
- 测试服：已结束测试对局建议保留 14 天；后续通过测试环境专属配置执行，绝不套用到正式服。
- 事故证据和最近正式 runtime 快照不进入自动清理；删除必须记录精确路径、大小、时间和保留的替代恢复点。

## 每周检查清单

- `df` 使用率与剩余字节；`matches.db`、WAL、平台库、站点媒体、回放表和快照目录大小。
- v1/v2 对局数量、最近 10,000 条命令平均 `state_json` 长度；v2 若不再等于 2 字节应立即阻止发布。
- 正式/测试活动链接、上一版本、systemd 状态、重启次数、8083/8084 与 WebSocket。
- 测试 releases、runtime backups、incoming、卡图哈希是否符合最小保留策略。
- 所有清理先列清单再执行，活动数据库与最新恢复点永不作为自动删除对象。
